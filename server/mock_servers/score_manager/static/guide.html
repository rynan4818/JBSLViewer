1. 独立したサーバの接続構成

中継と仮スコア管理は別フォルダ・別プロセスです。それぞれの start.bat でAPIと専用管理画面が起動し、Ctrl+Cでその組だけが停止します。管理画面へのログインは不要です。

Viewerの leaderboardApiUrl は http://127.0.0.1:18080/leaderboard/api/。仮スコアを使う場合の scoreServerBaseUrl は http://127.0.0.1:18082、allowDevelopmentHttp は true です。実スコアを使うときは、そのスコア提出先URLに切り替えます。

仮スコアの「リーグ取得先 URL」、または実スコアの jbsl_web_url に中継のベースURLを指定します。中継単独でも稼働できます。スコアサーバを起動する必要はありません。

既存の activeLeagueApiUrl と playlistSongsApiUrl は実JBSL-WEBのままです。設定変更は実JBSL-WEBへ送信されません。

2. Challenge の一生

reserved予約成功で1回消費
再送は同じ予約を返す
→
started開始通知を受理
→
submitted結果を受理
採用対象 / 対象外を記録

結果未受理のまま結果受付期限または現在の運用タイムアウトに達すると一覧では abandoned（受付期限切れ）です。運用タイムアウトは境界時刻を含めて失効します。結果受付期限ちょうどの扱いは設定で変わります。これは現在のスコアサーバ時計で計算した表示で、詳細にはDB保存状態も載せます。閲覧だけでデータは書き換えません。時計差を戻すと表示が戻る場合がありますが、API処理で既にabandonedに更新された状態は残ります。

開始前にブロックされた結果（preflight_rejected）は開始通知なしで提出されることがあります。開始時刻が空欄でも直ちに異常ではありません。

3. 提出スコアと Challenge を調べる

  1. 「提出スコア」でリーグID、SID、終了種別、ランキング採用可否を絞り込みます。1ページ25件。自動更新は5秒間隔です。
  2. 「詳細」で譜面・回数・予約から提出までの時系列・点数・コンボ・ミス・採用可否・無効理由・リプレイ保存有無を確認します。
  3. 「受信メタデータ JSON」には実際に届いた内容、「受理時の API 応答 JSON」には再送時も返す保存済み応答が表示されます。nullと0は異なる値です。
  4. 「Challenge」から未提出・期限切れの予約も調べられます。詳細の受付履歴で提出拒否の理由コードを確認します。
  5. Challengeが作成される前の認証・予約拒否は「受付履歴」に表示されます。結果一覧は受理済み結果だけです。API処理での拒否は受付履歴、API到達前の障害注入はAPI通信ログで確認してください。

ランキング採用対象は保存された validForRanking=true を意味します。この仮サーバはBSORの基本的な識別情報を検証しますが、点数の完全な再計算は行いません。対象外の結果でも回数は戻りません。

SIDは文字列の完全一致です。先頭の0は残します。Challenge ID / hashは部分一致で検索できます。表示時刻はJST、原文JSONの時刻はUTCです。

5. 予約で回数を消費する

reserve最新情報を再取得
成功確定で1回消費
→
startedゲーム開始通知
回数の追加消費なし
→
result結果・BSORを提出
中断でも回数は戻らない

上限はユーザー×リーグ×MapKeyごとに1〜100回です。リーグ全体で共有する回数上限はありません。同じ成功済みIdempotency-Keyを同じ内容で再送すると元の応答を返し、再取得・追加消費はしません。異なる内容で同じキーを使うと409です。

リーグ設定の上限を変更しても、確定済み予約の応答と提出の応答は変わりません。最新残数はstatusで確認します。実行状態の上限は最後の予約時点の値です。新しいテストSIDで、新しい消費枠を使って試せます。

6. 開始締切と結果受付期限

実効終了 = qualifier.ends_at があればその日時、なければ league.end
Viewer の開始締切 = 実効終了 − ゲーム内曲時間
結果受付期限 = 予約時の実効終了 + α（既定300秒）
Qualifier開始空欄は開始下限なし
開始締切終了−ゲーム内曲時間
実効終了設定した終了日時
結果受付期限実効終了+α

例: UTC 15:00終了、曲時間180秒、α=300秒なら、Viewerの開始締切は14:57、結果受付期限は15:05です。日本時間ではそれぞれ23:57、翌日00:05です。入力欄はUTC、一覧とログはJSTを明示しています。

予約時に確定した resultAcceptUntil は、後で猶予や期間を変えても維持します。一方、このモックの「期限一致を受理」「運用タイムアウト」は要求時の試験設定なので既存Challengeにも適用します。これは本番未確定ポリシーの実験用です。

サーバ開始判定は既定で「実効終了のみ」です。「実効終了−曲時間」ではfixtureの曲時間を使い、nullの場合は実効終了のみで判定します。Viewerのローカル曲時間による判断とは独立しています。

時計差設定はスコアサーバだけに適用します。OS・Viewerの時計は変えません。期限超過時は認証と所有者を確認してから期限を優先し、提出済み結果の期限後再送も409です。元の結果を消すことはありません。厳密な一致境界は、注入時計を使うPython/C#自動テストで確認します。

7. キャッシュを使う表示と最新情報による予約

status既定60秒まで再利用
上流到達不能なら取得後300秒まで参考表示
新規reserve毎回必ず中継へ取得
失敗時は消費せず拒否

参考キャッシュの300秒は取得からの総経過時間で、60秒へ加算しません。不正JSONや不正な設定の場合は参考表示にフォールバックしません。staleの情報で新規予約を認可しません。

リーグ設定を保存してもキャッシュは自動で消しません。仕様のTTL動作を再現するためです。すぐに反映を確認する場合は「実行状態 → リーグキャッシュを消去」を押し、Viewer側もリーグ情報を再取得してください。

8. 管理画面はログイン不要、Viewer はstub認証

管理画面はloopback専用です。ブラウザからの更新は同一Originと専用ヘッダーで確認するため、別サイトからの操作を受け付けません。ユーザー名やパスワードはありません。

ViewerのAPIは従来どおりticket → Cookie → auth/meです。このランチャーではstub認証を使い、非空のテストticketとsteamTicket/oculusTicketを受け、設定したSIDを返します。外部認証サービスへticketを送りません。認証プロバイダーを実際に試す従来の単独起動はREADMEを参照してください。

「テストSID」を変えたら「Viewerセッションを失効」を実行します。古いSIDのChallengeやOutboxを新しいSIDとして送ることはできません。SIDも接続先も、予約時の所有者を維持します。ポートを変えたスコアサーバはViewerにとって別の送信先です。

提出サイズとリプレイ

「サーバ挙動」で圧縮replay・展開後BSOR・metadataそれぞれの上限をバイト単位で変更できます。既定は16 MiB / 128 MiB / 512 KiBです。1 MiB = 1,048,576バイト。保存後に始まるリクエストから反映されます。

上限を小さくしてViewerから提出し、413で拒否されることとOutboxから再送されることを確認できます。上限を戻した後は同じ提出IDで再送します。受理済み結果の再送は重複保存しません。

gzipは受信後に展開して data/replays/ へBSORとして保存します。詳細画面のSHA-256とサイズは展開後データに対応します。提出データと受付履歴はSQLiteへ永続保存し、表示用通信ログは直近1,500件をメモリ内に保持します。

10. 中継ログと Swagger UI

各管理画面のSwaggerリンクは、それぞれ中継 :18080 または仮スコア :18082 の実APIを開きます。ライブラリを同梱しているため、オフラインでも画面を表示できます。Try it out は同じポートへ実際に送信し、注入した障害・遅延も適用されます。

スコアAPIは最初にauth/sessionを実行します。発行されたHttpOnly Cookieはブラウザが保持し、次のstatus等へ送ります。Idempotency-KeyにはUUIDを入力し、成功済み要求の再送では同じキーと本文を使います。resultのmetadataはJSON文字列で、採用候補のclear/failではBSOR gzipも必要です。ResultMetadataの全フィールドはSchemasにあります。

ログは直近1,500件をメモリに保持します。再起動で消えるため、必要なら「JSONを保存」で出力します。種類、HTTP status、所要時間、出所、Request ID、エラーコードで絞り込めます。スコアAPIが中継を取得するとき、同じRequest IDを引き継ぎます。

認証ticket・Cookie・クエリ文字列・要求本文・リプレイ本文はログへ記録しません。中継後のJSONを調べたい場合は、中継側のリーグ画面のプレビュー／保存済みAPI確認かSwaggerのレスポンスを使ってください。

Swagger UIのローカル配信は FastAPI公式の配信方法 に基づきます。契約の正本はリポジトリの docs 内の3つのAPI仕様書（Revision 9）です。
