公開Qualifier一覧とSID追加

開催中のQualifierリーグはログインせずに閲覧できます。ログイン画面からも開けます。実JBSL-WEBの開催中一覧にあり、中継サーバへ保存済みでQualifierが有効な実リーグが対象です。実一覧と保存設定の両方で開催中・受付中かつリーグ終了前である必要があります。未取込・無効・停止・終了したリーグと同梱サンプルは表示しません。

  1. 追加先のリーグ名とQualifier期間を確認します。期間はブラウザのローカル時刻で表示し、Qualifier開始前の事前登録も可能です。
  2. SIDを入力して「SIDを追加」を押します。前後の空白を除いた1〜128文字を受け付け、途中の空白・改行・制御文字は使えません。先頭の0や大文字小文字を保持し、SIDの本人認証は行いません。
  3. 「SIDを追加しました」または「このSIDは登録済みです」を確認します。追加は同一接続元で1分10回までです。手動参加者として保存し、中継APIへ反映します。再起動後も保持し、同じSIDを再送しても二重登録しません。

公開画面ではSIDの追加だけができます。削除・参加者の置換・その他の設定変更は管理者ログイン後に行ってください。ランキングのSID自動追加がONの場合、手動参加者から削除しても、ランキングに存在するSIDは中継時に追加されます。

実中継モードでは開催中一覧を60秒間再利用します。取得に失敗した場合は前回情報と表示し、更新できるまでSID追加を停止します。保存応答モードでは保存済み一覧と取得日時を表示し、上流へ取得に行かずに検証できます。必要な実リーグの一覧取得・取込・保存は、先に管理画面から行ってください。

1. 独立したサーバの接続構成

Viewerの leaderboardApiUrl は管理画面の「実行状態 → 接続先」に表示される設定を使用します。scoreServerBaseUrl は利用するスコアサーバの接続先を指定してください。allowDevelopmentHttp は接続先に合わせて設定します。HTTPのローカルスコアサーバを併用する場合は true が必要です。

仮スコアの「リーグ取得先 URL」、または実スコアの jbsl_web_url に中継のベースURLを指定します。中継単独でも稼働できます。スコアサーバを起動する必要はありません。

既存の activeLeagueApiUrl と playlistSongsApiUrl は実JBSL-WEBのままです。設定変更は実JBSL-WEBへ送信されません。

2. 実リーグの取込と保存

  1. 「実リーグ一覧を更新」で実サーバの /api/active_league を取得します。失敗時は前回の成功日時とエラーを表示します。前回データを最新結果とは扱いません。
  2. 開催中リーグの「取込・設定」を開きます。leaderboardとplaylist_songsを取得し、編集用の下書きを作成します。
  3. 取込直後のQualifierは無効、SIDの自動追加はONです。総合順位と各譜面のランキングにあるSIDを、中継のたびに重複を除いて追加します。追加のSIDは手入力するか「参加者追加用SIDを追加」を押します。チェックボックスをOFFにすると手入力分だけを返します。
  4. 有効チェック、方式、期間、譜面別上限を設定します。不明なCharacteristic・Difficultyは手入力します。曲時間はBeatSaverの /maps/hash/{hash} の metadata.duration（秒）から自動入力します。実中継モードで設定を開く際も取得し、保存で確定します。未設定分は実中継時にも補完します。取得失敗時は既存値（未設定なら空欄）を保持します。サンプルと保存応答モードの編集・中継では外部取得しません。
  5. 「JSONをプレビュー」で検証し、保存します。保存済みAPIは中継先へ実HTTPで要求し、その時点の障害設定も含む応答を確認できます。

保存は検証に成功した場合だけ行い、revisionを文字列のまま増加させます。未設定リーグは実JBSL-WEBのJSON本文をそのまま中継します。保存応答モードでも未設定リーグは実サーバへ接続します。設定済みリーグで元の譜面構成と設定が一致しなければ409 mock_fixture_invalidです。複数画面で同じリーグを編集した場合は、古いrevisionからの上書きを409で拒否します。

管理データは既定で jbsl_web_proxy/data/ に保存します。リーグ設定は control.json です。提出状態は仮スコア側の score_manager/data/score.sqlite3 と replays/ に保存します。未保存の取込下書きと表示ログは再起動で消えます。既存の jbsl_web_proxy/fixtures/ とルートの mock_score_server.db は管理画面から変更しません。

4. 譜面は3要素で照合

(hash, characteristic, difficulty)
(0123456789ABCDEF0123456789ABCDEF01234567, Standard, ExpertPlus)

hashは空白を除いて大文字へ正規化し、40桁のSHA-1を使います。Characteristic・DifficultyはBeat Saberの選択値です。同じhashでもExpertとExpertPlusは別譜面です。

中継への設定追加はlidを使います。lidが無い・重複する取込データではindexを明示します。実playlist APIからの補完はlidとhashが一意に一致する場合だけです。不明な難易度をhashから推測しません。元のtitle・scores・missなどは保持します。

実サーバ側で譜面が追加・削除されると保存設定との対応が変わる場合があります。全譜面への対応を検証し、欠落や重複は409にします。安定した再現には保存応答モードを使えます。

→
result結果・BSORを提出
中断でも回数は戻らない

上限はユーザー×リーグ×MapKeyごとに1〜100回です。リーグ全体で共有する回数上限はありません。同じ成功済みIdempotency-Keyを同じ内容で再送すると元の応答を返し、再取得・追加消費はしません。異なる内容で同じキーを使うと409です。

リーグ設定の上限を変更しても、確定済み予約の応答と提出の応答は変わりません。最新残数はstatusで確認します。実行状態の上限は最後の予約時点の値です。新しいテストSIDで、新しい消費枠を使って試せます。

6. 開始締切と結果受付期限

実効終了 = qualifier.ends_at があればその日時、なければ league.end
Viewer の開始締切 = 実効終了 − ゲーム内曲時間
結果受付期限 = 予約時の実効終了 + α（既定300秒）
Qualifier開始空欄は開始下限なし
開始締切終了−ゲーム内曲時間
実効終了設定した終了日時
結果受付期限実効終了+α

日時の入力・一覧・ログ・実効終了はブラウザのローカル時刻です。日本ならUTC+9で入力できます。例: ローカル時刻で15:00終了、曲時間180秒、α=300秒なら、Viewerの開始締切は14:57、結果受付期限は15:05です。保存値とAPIの日時はUTCに変換します。

予約時に確定した resultAcceptUntil は、後で猶予や期間を変えても維持します。一方、このモックの「期限一致を受理」「運用タイムアウト」は要求時の試験設定なので既存Challengeにも適用します。これは本番未確定ポリシーの実験用です。

サーバ開始判定は既定で「実効終了のみ」です。「実効終了−曲時間」ではfixtureの曲時間を使い、nullの場合は実効終了のみで判定します。Viewerのローカル曲時間による判断とは独立しています。

時計差設定はスコアサーバだけに適用します。OS・Viewerの時計は変えません。期限超過時は認証と所有者を確認してから期限を優先し、提出済み結果の期限後再送も409です。元の結果を消すことはありません。厳密な一致境界は、注入時計を使うPython/C#自動テストで確認します。

7. キャッシュを使う表示と最新情報による予約

status既定60秒まで再利用
上流到達不能なら取得後300秒まで参考表示
新規reserve毎回必ず中継へ取得
失敗時は消費せず拒否

参考キャッシュの300秒は取得からの総経過時間で、60秒へ加算しません。不正JSONや不正な設定の場合は参考表示にフォールバックしません。staleの情報で新規予約を認可しません。

リーグ設定を保存してもキャッシュは自動で消しません。仕様のTTL動作を再現するためです。すぐに反映を確認する場合は「実行状態 → リーグキャッシュを消去」を押し、Viewer側もリーグ情報を再取得してください。

8. 管理者ログインとViewerのstub認証

中継の管理画面はユーザー名とパスワードでログインします。初回管理者はサーバ起動時に運用者が作成します。管理者の追加・パスワード再設定は、サーバのフォルダで start.bat set-admin ユーザー名 を実行してください。パスワードはコンソールで確認入力します。独自の保存先を使う場合は通常起動と同じ --data-dir を指定します。

ログインは8時間有効です。終了時はサイドバーの「ログアウト」を押し、期限切れ時は再ログインしてください。パスワード再設定後は、そのユーザーの既存ログインも無効になります。スコアサーバの管理者とは別管理です。Viewer用中継API、Swaggerとこのガイドはログインなしで利用できます。

管理データの取得と設定変更にはサーバ側でも認証を要求します。ブラウザからの更新では同一Origin・専用ヘッダーとCSRFトークンを確認します。

仮スコアサーバのViewer向けAPIはticket → Cookie → auth/meの順に利用します。stub認証では非空のテストticketとsteamTicket/oculusTicketを受け、設定したSIDを返します。外部認証サービスへticketを送りません。認証プロバイダーを実際に試す従来の単独起動はREADMEを参照してください。

「テストSID」を変えたら「Viewerセッションを失効」を実行します。古いSIDのChallengeやOutboxを新しいSIDとして送ることはできません。SIDも接続先も、予約時の所有者を維持します。接続先を変えたスコアサーバはViewerにとって別の送信先です。

10. 中継ログと Swagger UI

各管理画面のSwaggerリンクは、それぞれ対応するAPIを開きます。ライブラリを同梱しているため、画面表示に外部CDNへの接続は不要です。Try it out はSwaggerと同じ接続先へ実際に送信し、注入した障害・遅延も適用されます。

スコアAPIは最初にauth/sessionを実行します。発行されたHttpOnly Cookieはブラウザが保持し、次のstatus等へ送ります。Idempotency-KeyにはUUIDを入力し、成功済み要求の再送では同じキーと本文を使います。resultのmetadataはJSON文字列で、採用候補のclear/failではBSOR gzipも必要です。ResultMetadataの全フィールドはSchemasにあります。

ログは直近1,500件をメモリに保持します。再起動で消えるため、必要なら「JSONを保存」で出力します。種類、HTTP status、所要時間、出所、Request ID、エラーコードで絞り込めます。スコアAPIが中継を取得するとき、同じRequest IDを引き継ぎます。

認証ticket・Cookie・クエリ文字列・要求本文・リプレイ本文はログへ記録しません。中継後のJSONを調べたい場合は、中継側のリーグ画面のプレビュー／保存済みAPI確認かSwaggerのレスポンスを使ってください。

Swagger UIのアセット配信は FastAPI公式の配信方法 に基づきます。契約の正本はリポジトリの docs 内の3つのAPI仕様書（Revision 9）です。
