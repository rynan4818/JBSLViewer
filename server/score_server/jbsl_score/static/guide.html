スコア管理ガイド

予約から結果の採用まで。管理画面の数値や設定が、どの処理に影響するかを図と具体例で確認できます。

画面の「?」は短い説明、各説明のリンクはこのページの該当箇所を開きます。ここに示す値は初期値・説明用の例です。現在の設定は管理画面で確認してください。

01 / LIFECYCLE

Challengeは予約から始まる

ユーザー・League・譜面の組合せごとに、予約成功で1回を消費します。結果を受理すると「提出済み」になります。結果の受理と、ランキングでの採用は別の判定です。

結果が届かなかった場合

結果受付期限または運用タイムアウトを超えると、15秒間隔の保守処理で「未提出・期限終了（abandoned）」にします。返却条件でabandonedを有効にしていた予約だけ、1回を返却します。

同じ予約・結果を同じキーと内容で再送しても、Challenge・結果・回数消費は増えません。再送の内容を変更すると競合として拒否します。

02 / DEADLINES

「予約の締切」と「提出の猶予」を分ける

実効終了日時 E はJBSL-WEBの qualifier.ends_at、未指定ならLeagueの end です。提出猶予 G の既定は300秒です。

設定何に適用するか例
新規Challengeの開始締切新しい予約を受け付ける最終時刻。標準はE。曲時間方式はE−上流の曲時間。E=21:00、曲3分なら曲時間方式の予約締切は20:57。
終了後の提出猶予予約済み結果の提出・再送をE+Gまで許可する。予約時に固定。E=21:00、G=300秒なら受付期限は21:05。
予約からのタイムアウト未提出のまま予約から指定秒数を超えたChallengeを終了する。0は無効。予約時に固定。20:58に予約、120秒なら21:00を超えて未提出の結果を拒否。猶予より先に終了する。

曲時間方式では上流の song_duration_seconds が不明な譜面の新規予約を拒否します。Viewer自身の曲時間による開始判定も行われます。運用タイムアウトは受理済み結果の期限内再送には適用しません。

猶予を変えて受付期限を確認する

終了時刻を21:00:00とした例です。サーバ設定は変更しません。

受付期限 21:05:00

0～604800秒（7日間）。新規予約の締切はこの計算では延びません。

どの瞬間の時刻で判定するか

  1. 認証・所有者確認
  2. Challengeの排他取得
  3. サーバ時刻で期限判定
  4. 本文の読込み・検証・保存

画面上の終了時刻やクライアント申告時刻ではなく、本文を読み始める直前のサーバ時刻を使います。期限内に受け付けた処理は、検証中に保守処理に終了扱いされないよう保護します。本文読込みには別途時間・容量上限があります。

03 / REFUNDS

「対象外の受理」と「提出の拒否」は違う

自動返却するかは、予約時に有効だった条件と、そのChallengeで受理した終了結果から決めます。初期設定はすべて返却なしです。運営判断による手動返却は、この設定にかかわらず操作できます。

条件返却判定の対象運用上の意味
開始前の失敗preflight_rejected、プレイ観測0回、開始通知なし。予約したがプレイに入れなかった場合。
開始時の失敗preflight_rejectedで、プレイ観測または開始通知あり。プレイに入った記録がある場合を独立して設定。
中断 / Quitquitとして受理した対象外結果。有効にすると中断して再挑戦できる。
Restartrestartとして受理した元Challengeの結果。再挑戦は新しい予約。元Challengeを上書きしない。
終了理由不明unknownとして受理した対象外結果。結果が届かない状態とは別。
スコア提出無効clear / failでも標準提出が無効。invalidReason=submission_disabled。Quit・Restart等があればそちらを優先。
Replay生成失敗clear / failでReplayを用意できない。invalidReason=replay_unavailable。壊れた添付Replayを拒否したケースは含まない。
結果未着・タイムアウト未提出のまま期限を超えてabandonedを確定。故意の未送信も区別できず、再挑戦可能になる。

clearだけでなくfailもランキング対象になり得ます。スコア値・標準提出許可・Replay等の条件を満たした結果が対象です。

API実装者向け: 終了理由の組合せ

04 / ATTEMPTS

通し番号と、残回数を区別する

未返却の使用回数 = 総Challenge数 − 返却数
残回数 = max(0, 上限 − 未返却の使用回数)

回数はSID × League ID × hash・characteristic・difficultyで分けます。ユーザー画面の「上限・残回数」は最後に検証した上流キャッシュが基準で、上限が不明なら「—」です。新規予約の時点では上流の最新上限を使います。

05 / MODERATION

取り消しても記録を残し、復元できる

詳細画面で提出内容を確認し、操作理由を1～500文字で記録して取消・復元します。元のmetadata・Replay・Challenge回数は変わりません。

現在ランキング対象 = 元の結果が対象 AND 取消されていない

validForRanking は元の対象資格、canceled は取消状態、effectiveForRanking は現在の採否です。元から対象外の結果を復元してもランキング対象にはなりません。

操作バージョンは提出ごとに保持します。他の管理者が先に変更した古い画面からの操作は409で拒否します。再取得して現在の状態と理由を確認してから操作してください。変更は監査ログと連携差分の両方に残ります。

REPLAY

提出したReplayをブラウザで再生する

提出結果の「BeatLeaderで再生」「ArcViewerで再生」を押すと、別タブでその提出のReplayを開きます。既存の「Replayをダウンロード」も利用できます。

選んだ外部ビューアに、このReplayだけを取得できる閲覧用URLを渡します。URLは最長10分間有効で、発行元の管理者がログアウトした場合も失効します。URLを知った人は期限内に取得できます。読み込み済みのデータは回収されません。

HTTPSでの配信と、対応する譜面・音源の取得が必要です。ボタンが無効な場合はAPI公開URLのHTTPS設定を確認してください。未公開・削除済みの譜面は、別途譜面ZIPを選ぶ必要がある場合があります。

ポップアップが抑止された場合は、提出結果に表示される「再生ページを開く」を押してください。期限切れの場合は再生ボタンからもう一度開いてください。

06 / INTEGRATION

資格は上流から、結果は差分で連携する

キャッシュの見方

通常キャッシュは既定60秒。上流到達不能時に取得から300秒以内なら、statusに参考情報と stale=true を返す場合があります。新規予約では常に上流へ問い合わせ、障害時は予約せず回数も消費しません。予約済みの結果提出は上流の復旧を待ちません。

差分の取り込み

  1. CLIで読取り専用Bearerを発行し、JBSL-WEBの秘密設定へ保存する。
  2. 初回はafter=0でchangesを取得する。seqは昇順、イベントはsubmitted / canceled / restored / attempt_refunded。
  3. submissionIdをキーに提出履歴を保存し、同じトランザクションでnextCursorを保存する。attempt_refundedも最新スナップショットとして反映する。
  4. 失敗時はcursorを進めず再取得する。Leagueフィルタごとに別cursorを保持する。

イベントのsubmissionはその時点の値です。現在の採否は単一提出取得、またはleaderboardで確認します。自己ベストはユーザー・譜面ごとのmodifiedScore最大、同点の自己ベストは受信が早いもの、同点順位は1,1,3方式です。

サーバを過去のバックアップへ復元した場合、外部のcursorが復元先DBより先に進んでいることがあります。取り込み先の履歴・cursorを復元時点と整合させて再構築してください。詳しいパラメーターはSwaggerのjbsl-web連携APIにあります。

07 / OPERATIONS

設定の適用時点と、復旧の手順

項目適用時点
猶予・運用タイムアウト・返却条件新しい予約から。既存Challengeは予約時設定を維持。
受付可否・開始締切方式・同時Challenge数新しい予約の判定から。既存予約の提出期限は変えない。
Viewerセッション時間・同時セッション数次のViewer認証から。既存セッションの期限は変えない。
キャッシュ・要求制限・ディスク下限保存後の各要求の判定から。
自動バックアップ間隔・保持数次の保守処理・バックアップ作成から。
ポート・URL・認証キー・HTTPSconfig.json / 環境変数の変更後、サーバを再起動。

設定は全項目とリビジョンをまとめて保存します。409 settings_conflictなら別の操作で設定が変わっています。画面を更新して、最新値を確認してから保存してください。「更新」は未保存の入力を破棄して再取得します。

バックアップ

既定は24時間ごと・7世代。概要の「バックアップを作成」でも実行できます。SQLiteのバックアップ機能でReplayを含むDBを保存し、整合性・回数集計・Replay SHA-256を検証してから確定します。作成成功後に保持数を超える古い世代を削除します。

復元する場合

  1. サーバを停止する。
  2. CLIでバックアップを別の新しいデータフォルダへ復元する。既存DBへの上書きはしない。
  3. config.jsonのdata_dirを復元先に変更する。
  4. 管理者は再ログインし、サービス用Bearerを再発行する。復元ではViewer・管理セッションとサービス用トークンを失効させる。
  5. JBSL-WEBの取り込み履歴とcursorを整合させてから連携を再開する。
.venv\Scripts\python.exe -m jbsl_score backup
.venv\Scripts\python.exe -m jbsl_score check
.venv\Scripts\python.exe -m jbsl_score restore data\backups\<バックアップ名>.sqlite3 data-restored

起動設定を別ファイルにしている場合は、各コマンドの jbsl_score の後に --config <設定JSONの絶対パス> を指定します。公開運用のHTTPS・OS権限・監視などは同梱の docs/OPERATIONS.md を参照してください。

08 / ACCESS

3種類の認証を使い分ける

利用者認証用途
JBSLViewerSteam / Oculus ticket → jbslq_session Cookie本人の資格確認・予約・開始・結果提出
JBSL-WEBサーバCLI発行の読取り専用Bearer差分・現在スコア・残回数の取得
運営管理者管理者名・パスワード → jbslq_admin Cookie管理画面。変更にはX-CSRF-Tokenも必要

それぞれの認証は相互に代用できません。管理ログインは8時間、同時5セッションまで。管理者作成・パスワード変更はCLI set-admin で行い、その管理者の既存セッションを失効させます。

Viewer認証は既定5要求/IP/分、status・meはそれぞれ60要求/ユーザー/分、予約は30、結果と開始通知はそれぞれ30が既定です。管理ログインは固定5要求/IP/分です。429では60秒待ち、同じ要求内容・キーで再送します。受付期限は待機中にも進むので、規模に合わせて制限と猶予を設定してください。

Swagger UIとこのガイドは管理用ポートでログイン前から閲覧できます。API仕様だけを表示し、実データの取得には従来どおり認証が必要です。Swaggerの実行ボタンは無効です。

09 / TROUBLESHOOTING

状況から確認する場所を選ぶ

操作・受信ログの「所要時間」は、サーバでの受付・操作開始からログ記録までのミリ秒（ms）です。受信・上流通信・処理の待機を含みます。過去の未計測ログは「—」と表示します。

状況・エラー確認する内容
結果未着Challenge ID、状態、受付期限、予約時タイムアウト。未知の終了結果を受理したunknownとは区別する。
409 result_acceptance_expired予約時の受付期限とサーバ受付時刻。既存予約は現在の猶予設定では延長されない。
409 attempts_exhausted該当ユーザー・League・譜面の未返却の使用数と、上流の最新上限。
409 idempotency_conflict / result_conflict再送キーと内容が初回と同じか。別の終了結果を同じChallengeへ送っていないか。
422 replay_invalid / replay_mismatchmetadataとReplayのSID・プラットフォーム・MapKey・multipliedScore・ゲームバージョン。
401 / 403 csrf_rejected再ログイン。更新操作のCSRFと管理画面URL。Viewer用と管理用の認証を混同していないか。
429要求数制限と再送間隔。監査一覧には保存しないため、応答のrequestIdとエラーログも確認。
502 upstream_invalid / 503 upstream_unavailableJBSL-WEBの稼働、URL、Qualifier応答形式、キャッシュの取得エラー。
503 storage_unavailableディスク空き下限・DBロック・ファイル権限。必要な空き容量を確保する。
バックアップ失敗概要の失敗表示、保存先容量、data/logsのエラー。成功した最終バックアップ日時も確認。

requestIdで画面の拒否記録と data/logs のログを照合できます。監査一覧は秘密のticket・Cookie・パスワードを保存しません。操作理由などの運営情報は記録に残ります。

10 / CHALLENGE CONTROLS

進行中を強制終了し、消費した回数を返却する

  1. 管理画面の「ユーザー」で対象者の「提出状況を確認」を開く。
  2. 予約済み・プレイ中のチャレンジ行で「強制終了」を選ぶ。
  3. SID・League・譜面・Challenge IDを確認して、操作理由を入力する。返却も必要なら「同時に1回返却する」を選ぶ。
  4. 確定後、状態と譜面ごとの使用・返却・残回数を確認する。

終了済みの未返却チャレンジには「1回返却」を使用できます。自動返却設定がOFFでも操作でき、1つのチャレンジで返却できるのは自動・手動を合計して最大1回です。返却済みは再度返却できません。

強制終了と返却の扱い

返却を選ばず強制終了した場合、消費回数を維持します。その後の期限処理でも自動返却されません。必要になったときは「1回返却」を操作します。提出済みのスコア・Replay・ランキング採否は、手動返却をしても維持します。

強制終了後はサーバで開始通知・結果提出を受け付けません。参加者のBeat Saberを遠隔停止する機能ではありません。Viewerのローカル送信待ち記録は参加者側で確認します。

結果提出が先に確定した場合、強制終了は409で拒否します。画面を更新して最新状態を確認してください。同じ操作の再送で回数を重複変更しません。強制終了済みへの再送で返却チェックだけを変えても追加返却は行わず、「1回返却」を別途操作します。

操作・受信ログのchallenge_force_endedが強制終了、attempt_refundedが返却です。管理者名、理由、変更前後を記録します。残回数はViewer・JBSL-WEBの次回取得から反映されます。提出済みへの手動返却はattempt_refunded差分イベントにも記録します。
